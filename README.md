# Roller Derby Replay — RK3588 录制节点 + DGX 监看台

本仓库当前默认是 RK3588 版本。原 Jetson 版本保留在 Git 历史及 archive/jetson-20261120 分支，DGX原 /home/ifit/xjh 运行目录不被本次发布覆盖。

## 架构
每台RK3588接一台Hikrobot USB3相机，采集2448×2048 BayerGR8约59.2fps；CPU去马赛克/转NV12，FFmpeg hevc_rkmpp硬编HEVC CBR 30Mbps。录像写节点本地，原分辨率主码流经9101到DGX；DGX NVDEC解码并本地缩放。无需第二路缩略编码，thumb-port必须为0。
默认入口现为体育赛事回放平台：左侧原比例紧凑四宫格、右侧集中控制、底部四轨共同时间轴；支持统一启停、四路联动回放、后台预载、即时回看、赛事绑定和软件时间校准。也保留单路入口。不提供硬件同步触发。详见 [平台使用说明](docs/SPORTS_PLATFORM.md)。

## 快速开始：DGX
```bash
cp nodes.example.json nodes.local.json
# 修改每个节点的地址及SSH别名，并建立 BatchMode SSH密钥连接
bash deploy/bootstrap.sh dgx --install-packages
python3 deploy/check_env.py --role dgx
python3 deploy/deploy_node.py --config nodes.local.json --node rk2
./run_multi.sh --config nodes.local.json
# 仅打开一台时：./run_studio.sh --config nodes.local.json --node rk2
```
DGX的NVIDIA驱动/NVDEC来自DGX系统，普通Ubuntu安装GStreamer包不保证有nvh265dec。不要用安装CPU版opencv的pip环境替代系统Python。

## 节点编号与隔离
示例：rk1=.100 / SSH rk3588 / 裁判端口8611；rk2=.101 / rk3588-2 / 8612；rk3=.102 / rk3588-3 / 8613；rk4=.103 / rk3588-4 / 8614。
各节点独立IP，可以分别使用同一9100回放、9101直播端口。DGX裁判HTTP端口必须各不相同。
节点录像 ~/hk_record；DGX状态/缓存/日志 ~/.local/share/roller-derby-replay/<node>/；默认归档 ~/录像_rk/<node>/。节点配置和账户凭据不提交。

## 界面布局
主操作字号为 14pt，面板标题 16pt，状态文字 12pt，按钮高度 44px。连接、录制、播放状态和实际显示帧率集中在各视频区域外的顶部状态栏；视频内不再叠加状态文字。状态栏沿用深色背景，第一行分别显示机位名和帧率，第二行显示录制、连接与播放状态；使用自适应网格和文字换行，避免窄窗口中互相遮挡。右侧保留操作和赛事标记，移除重复机位状态卡、卡片副标题和说明小字。录像管理同步增大字号及行高。小窗口可滚动侧栏访问全部操作。

已检查 2560×1440 与 1200×800 的四宫格、放大及完整画幅。四路后台持续录制时，UI 验收测得四宫格回放每路约 59.05–59.11 fps、RK4 放大约 58.70 fps。

## 比赛计时与时间轴
先开启本场录像，再按「比赛开始」，独立比赛时钟从 `00:00` 正向计时。「暂停比赛 / 继续比赛」只控制比赛计时，录像保持连续，也不改变回放的播放/暂停状态。不提供分秒输入框。

- 比赛开始时刻按 DGX 当前时间记录，不使用可能正在回放的历史画面时间。比赛起点与停表/继续转换随场次保存，重开界面恢复；首段尚未封存时也保存明确机位目录及校时信息。
- 开始前仍显示录像时间与「比赛未开始」。开始后，时间轴刻度、回放指针及标记显示比赛时间；赛前录像显示「赛前」，暂停区间显示「暂停于对应比赛时间」，并以灰色区域标识，比赛零点显示绿色标线。
- 鼠标悬停或拖动时间轴时显示该位置对应的比赛时间，移出后隐藏提示。底层定位始终使用连续录像坐标，因此暂停期间不同画面仍能独立定位，不会跳到同一个录像位置。
- 所有录制停止后冻结对应比赛计时；即使正在查看另一场比赛，也会保存实际结束录制场次的停表状态。切换比赛会读取各自的计时记录；既有未设置起点的录像不会被自动猜测比赛开始时间。
- 这是基于现有软件校时与视频索引的映射，不等同于相机曝光硬件同步；时间轴可定位范围仍由已可读取的视频分段决定。

## 回放显示帧率
回放窗口已移除原约 20 fps 的绘制限制。使用复用 ImageTk 图像缓冲替代逐帧 PPM 上传，视频更新与状态栏刷新分离；时间轴复用静态轨道，分段切换时在后台释放旧解码器。右侧机位状态显示近两秒实际提交绘制的不同视频帧率，暂停或隐藏机位不会继续按录像标称帧率计数。

在 2560×1440、59.95 Hz 屏幕上，以已有四路长录像进行 1x 回放：四宫格连续 60 秒实测每路 59.14–59.21 fps；四台分别放大 20 秒为 58.99–59.24 fps。该结果为应用绘制计数，并非外部测量屏幕扫描输出；不保证所有负载下零显示跳帧，也不代表相机采集无丢帧。原录像分辨率、编码和文件不变。详见 [实测记录](docs/validation/2026-11-22-display-fps.json)。

四路真实相机直播亦完成验收：四宫格连续 60 秒实测每路 58.67–59.23 fps；四台分别放大 15 秒为 59.01–59.19 fps，均接近约 59.2 fps 的视频源。本次测试四路持续在线，未触发为追赶积压而丢弃压缩帧；不代表所有负载或长期 USB 采集均零丢帧。详见 [直播实测记录](docs/validation/2026-11-22-live-display-fps.json)。

DGX 新增依赖 `python3-pil`、`python3-pil.imagetk`，已纳入环境安装与检查脚本。

新比赛目录先于首个完整分段出现时，时间轴保持等待状态；只有实际分段到达后才初始化比赛起点。空机位不作为零时间参与计算，防止绝对时间戳被显示成几十万小时的比赛时长。已用空目录、延迟到达、校时及跨比赛切换测试，并对真实约 339.75 秒场次验证起点和后段四路定位。

## 比赛计时与赛事事件

先开启本场录像，再在独立的「实时比赛时间」卡片按「开始」。暂停/继续只影响比赛计时，录像保持连续。按「比赛结束」并确认后，比赛时间冻结，录像继续，可保留赛后画面；开启新场录像后可重新计时。

底部不再显示「共同赛事时间轴」标题。保留四路联动进度条，回放时其旁边显示所选机位当前实际视频帧对应的比赛时间；定位加载期间显示「回放定位中」。右侧实时计时独立运行。鼠标悬停或拖动仍显示目标位置的比赛时间，暂停期间的不同录像位置保持可选。

进度条默认开启「全程自适应」，随录像增长、窗口大小自动调整比例，始终覆盖本场从头到尾。普通滚轮不再改变时间范围。需要局部细节时可点「＋」或 Ctrl+滚轮主动放大；点「全程自适应」恢复整场视图，按钮蓝色表示已开启。

开始、暂停、继续、结束自动写入赛事事件，并保存比赛时间及 DGX 真实时刻。选择事件后「跳转」可联动回放；尚未完成写入的时刻提示等待录像就绪。自动事件同样支持修改备注和删除。旧比赛的计时记录首次打开时补成事件，删除后不会再次生成。计时状态随本场赛事保存并在重开后恢复。

## 录像与存储管理
监看台顶部及右侧「赛事录制」卡片均有「录像管理」入口。列表以**比赛**为单位，每场一行，展开显示 RK1–RK4 的视频、时长及存放位置。选择任意机位明细也代表选择整场比赛。支持比赛搜索、归档状态筛选和多场批量操作。

- 「回放整场比赛」统一打开本场四路录像；保留时间校准和赛事标记，缺少机位明确显示不完整。
- 「归档整场至 DGX」复制并校验本场全部可用 RK 视频，保留原件。使用 rsync 断点续传和 SHA-256 核对；中断的 `.partial` 目录不计为完整归档。每场显示已校验归档机位数，例如 `4/4`。
- 「清理本场 RK 副本」只删除所选比赛在 RK 上的全部机位原件，确认框说明 DGX 归档是否完整；DGX 副本保留。
- 「删除整场比赛」删除所选比赛所有机位的 RK 原件及 DGX 归档，确认框说明整场范围、机位数和总占用。若节点或归档目录读取失败，拒绝整场删除，避免遗漏未读到的副本。
- 比赛归属使用平台保存的赛事记录，结合每个节点的明确录像目录绑定；同一机位两处副本合并显示。同一场的重复查看记录不会生成重复比赛。不把时间相近的独立录制猜成一场；没有赛事记录的历史素材显示为不完整比赛。
- 节点正在录制时拒绝其归档和删除；后台操作期间禁止从平台启停录像。删除前重新核对目录身份与进程，只允许配置根目录下的直接录像子目录，拒绝符号链接。逐项报告任务结果，日志为 `~/.local/share/roller-derby-replay/storage-operations.jsonl`。
- 删除副本后自动更新比赛引用：有剩余副本则切换来源，否则移除录像引用和本场缓存。容量按每路 30 Mbps（13.5 GB/小时）估算；RK 扣除 10 GB 停录预留，DGX 显示四路归档容量。约每 30 秒刷新，也可手动刷新。

无需给 RK 安装新的依赖；沿用 SSH 密钥、Python 3 与 DGX/RK 两端的 rsync。管理范围为配置的节点录像目录与各机位的 DGX 归档目录，不包含其他个人视频文件。

## 新RK3588环境契约

四台 RK 均须安装开机性能服务，同时将 BSP 的 cpufrequtils 默认 governor 配置为 performance，避免启动顺序竞争。固定有线地址和自连接配置应持久保存。DGX 保留手动打开监看台、手动开始录像；不安装监看台自启动。设备启动完成后，可在 DGX 执行 `python3 deploy/verify_boot.py --wait 120` 检查五台就绪状态，之后正常打开桌面快捷方式并按「全部开始」。完整规范及重启验收见 [部署规范](docs/DEPLOYMENT.md)。

详见 [部署规范](docs/DEPLOYMENT.md)。必须先安装厂商兼容BSP、MVS和带Rockchip硬编的FFmpeg；部署脚本只安装/核验通用依赖，不会刷机、编译或凭空安装私有SDK。
`deploy_node.py` 拒绝覆盖正在录制的节点，先备份旧入口，再上传代码、应用有记录的运行时性能配置，最后严格检查相机USB3速率。检查失败不是部署成功。

## 已知限制
- USB长期可靠性尚未解决：参考节点曾运行约52分钟后usb_submit_urb返回-19(ENODEV)。启动前DeviceReset是恢复措施，不是根因修复；录制中不自动重启来掩盖丢帧。
- 录制连续5次取帧失败会写camera_alarm.json并退出；启动须确认实际编码输出，不能只看进程存活。
- 异常退出尾段元数据可能时长为0，视频可能可解码；恢复原始文件前请备份，尚未修复此问题。
- 用户已完成约64–65分钟四路实录，元数据跨度已核对；新版另外完成联动回放和统一启停实机验收。此结果不表示USB控制器问题已经根治。每路30Mbps，四路约120Mbps；归档/回放突发流量需要另行限速。
- 整场时间轴默认从0秒自动缩放，直播计时跟随新画面，历史回放不会只剩最近十分钟。
